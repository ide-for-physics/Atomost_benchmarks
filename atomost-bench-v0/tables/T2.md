# T2 · 参谋唤醒策略账本（atomost-bench v0）

> **P0 是真实记录**（2026-10-07 14:50 → 2026-10-17 12:21）。**P1–P4 都是模拟（SIMULATED）**：在同一份每小时检查记录上重放，没有真的跑。这次重放没有调用任何模型。

## 先说结论

- 10 天里，五个项目的参谋（strategist，每个项目一个常驻的 Claude 会话）一共跑了 **27 轮**：14 轮由定时器自动叫醒，6 轮由人通过 `atomost strategist message` 发起，7 轮是启动。按 v1.41 口径算共 **$223.68**（另有 memory-control 早期试跑 $1.90）。做了 **806 次记忆动作**，处理了 **41 条 memo**（17 条写进记忆，24 条跳过）。
- **自动唤醒的实际花费（P0）：14 轮，$48.86。** 同样的检查记录下，如果每小时都做一轮完整复查（P1），是 435 轮、约 $996（区间 $626–2,101）；每次检查到显著变化就做一轮、不设每天上限（P2），是 303 轮、约 $694；每天固定做一轮（P3），是 23 轮、约 $53；常驻会话每小时看一眼（P4），约 $589，缓存是热是冷，能让它在 $44 到 $659 之间变。
- **P0 的代价是等待。** 从"检查到显著变化"到"参谋真的处理"，中位数 9.2 小时，最坏 73 小时。几次最长的等待不是因为策略慢，而是出了故障：cophon 的参谋屏幕连续 3 天没有输入框（53 次本该叫醒、没叫成）；10-16 那次唤醒一开始就撞上 Fable 额度，什么也没做，却占掉了当天唯一一次自动唤醒，变化于是等了 47 小时。

## 方法

**检查记录**来自每小时跑一次的检查服务的日志（`journalctl --user -u atomost-strategist.service`，2,493 行，副本存于 `benchmarks/atomost-bench-v0/results/t2/strategist_journal.txt`）。每个项目每小时一次检查，结果分四种：没有显著变化；有显著变化并叫醒了参谋；有显著变化，但因为"每 24 小时最多自动叫醒一次"被压住；有显著变化，但参谋屏幕上没有输入框、没叫成。

**每一轮的边界**取自 `projects/<id>/strategist/rounds/` 的目录名（目录名就是开始时间）。一轮到下一轮开始为止。中途如果人在参谋会话里另起话头（这一轮已经有过一次完整回复，之后人直接打字），从那一刻起的部分单独记为"人接着谈"，不算这一轮自己的花费。

**token 和美元的算法与 v1.41 一致**：一条回复按 message.id 只算一次；参谋会话自己的子代理（`<会话>/subagents/*.jsonl`）也算进去；每条回复按它自己用的模型定价（直接调用 atomost 的 `usage_key`、`subagent_files`、`price_for`、`_dollars`，价目表是 `projects/prices.yaml`）。

**记忆动作**是这一轮时间窗里 `memory-log.jsonl` 中 `by = strategist` 的行。**memo** 是 `notes/*.json` 里由参谋处理掉的条目（写进记忆或跳过）。

**每轮成本模型**（P1–P3 都用它）：取实际定时器轮次"自己那部分"的花费，13 轮（去掉 1 轮 0 次调用就失败的）。中位数 **$2.29**，四分位 $1.44–4.83，用来给出区间。如果把人接着谈的部分也算进去，中位数是 $4.83，P1–P3 的金额要大约翻一倍。

**P4 的单次成本**按各项目参谋主会话实测算：上下文中位数（cophon 20 万 token，其余 12–17 万），每次输出的中位数（约 700–1,700 token），以及实测的缓存命中情况。距离上一次调用不到 55 分钟时，97–98% 的上下文是从缓存读的（686 次调用）；超过 65 分钟时只有 11%（20 次调用）。每小时一次的检查间隔总是略长于 60 分钟，所以中间值按 11% 命中算，区间的低端假设缓存一直热，高端假设完全冷。

**"变化→处理"延迟**：从某次检查第一次看到显著变化，到下一次真正处理为止。P0 的"处理"取一轮里第一条成功回复的时间，所以一开始就失败、什么也没做的轮次不算处理。模拟策略假设每一轮都能顺利跑完，人发起的轮次照旧计入。P1、P2、P4 正好在看到变化的那次检查上动手，所以延迟按定义是 0。变化本身发生到被检查发现之间还有最多 1 小时，这对所有策略都一样，没有计入。

## 这份表不能说明什么

- **P1–P4 没有真的跑过。** 它们的花费是"轮数 × 实测的每轮成本"，这个成本只来自 13 轮定时器轮次，样本小，而且混了 Fable 5.1 和 Opus 5.5 两种模型。如果每小时都复查，每一轮要处理的变化会更少，单轮可能更便宜；常驻会话的上下文会越积越长，单次可能更贵。这些都没有模拟。
- **显著变化的记录是在 P0 下产生的。** 实际中每做完一轮，"自上次复查以来"的计数就清零。换成别的策略，哪几个小时算"显著"会不一样，P2 和 P3 的轮数只是近似。"计数器重置"那一行是粗估。还要注意，到今天 12:55 修好 v1.41 之前，检查用来判断"新花销 ≥ $20"的数字是旧算法算的，有重复计数。
- **延迟为 0 是按定义得出的，不等于真实效果更好。** 模拟策略假设每一轮都顺利跑完；P0 最坏的几次等待恰恰来自故障（屏幕没有输入框、额度用完）。同样的故障放到 P1–P4 里也会发生，模拟没有计入。P4 的短回合只是看一眼，能不能当场处理变化，没有验证。
- **只说明花了多少、等了多久，不说明复查做得好不好。** 记忆动作和 memo 只是计数，不是质量。
- **美元是按标价推算的**，不是账单。opus-5-5 那一行在价目表里标着"待核"；opus-4-8、sonnet-5-5 没有价目行。新日报和体检的金额来自 Claude Code 自己的价表，和 prices.yaml 不是同一个来源。
- **能对照的时间很短**：新日报只跑了 3 天，体检 2 天，参谋 10 天，只覆盖五个项目。
